Methodology
Technical explanation of the Business Entity Resolution pipeline.
1. Problem Statement

Given three independently collected datasets of business entities (Source 1, Source 2, Source 3), the task is to identify, for every Source 1 entity, the zero or more matching entities in Sources 2 and 3. Sources contain noise: spelling variations, abbreviations, OCR errors, missing fields, and different address formats.

2. Dataset

All data is provided as TSV files with columns: entity_id, business_name, business_address, country. Countries are open-set — the system supports any country (US, France, Germany, India, etc.) without hard-coding. The test set includes French records.

3. Data Preprocessing

Each source is loaded with pd.read_csv(file, sep="\t"). Data validation checks for required columns, missing entity IDs, and duplicate IDs. Countries are reported but never filtered.

4. Name Normalization

Unicode NFKD → ASCII, lowercase, &→and, punctuation removal, legal suffix normalization (Ltd→limited, GmbH, SARL, Inc, Corp, …), common abbreviations (Technology→tech, Solutions→sol, …), whitespace normalization.

5. Address Normalization

Same Unicode/lowercase pipeline. Digits preserved (street numbers, ZIP codes). Common abbreviations: Street→st, Avenue→ave, Boulevard→blvd, Suite→ste, etc. Postal code patterns extracted for blocking.

6. Candidate Blocking

Six strategies are applied in sequence, each adding to the candidate pool: (1) Exact normalized name, (2) Name token overlap (inverted index), (3) Country + name token, (4) Address token overlap, (5) Postal code token, (6) TF-IDF character n-gram cosine (threshold 0.25). Only S1→S2 and S1→S3 pairs are generated — never S1→S1.

7. Feature Engineering

16 features per candidate pair: exact name/address match, RapidFuzz token sort ratio, Levenshtein similarity, Jaccard on name/address tokens, TF-IDF cosine (name + address), numeric token overlap, address RapidFuzz ratio, country match, common token count, number Jaccard.

8. ML Model

LightGBM gradient-boosted classifier trained on labeled positive pairs (from ground truth) and hard-negative pairs (candidate pairs that are NOT in ground truth). Returns a probability score per pair.

9. Hard-Negative Training

Hard negatives are non-matching candidate pairs sampled from the blocking output. These are more informative than random negatives because the model must learn to distinguish near-misses.

10. F0.5 Optimization

After training, a threshold sweep (0.05 – 1.0) is run on the validation set. The threshold maximizing macro F0.5 is selected. F0.5 = (1.25 × P × R) / (0.25×P + R). This penalizes false merges more than missed matches.

11. Singleton Handling

If no candidate pair exceeds the threshold for a Source 1 entity, it is declared a singleton (no match). Correct singletons score F0.5 = 1.0. False merges (predicting a match for a true singleton) score F0.5 = 0.0.

12. Output Generation

matching_results.tsv: source1_entity_id → matched_entity_ids (comma-separated, or empty). candidate_pairs.tsv: source1_entity_id → candidate_entity_ids. Both are tab-separated. Every S1 entity has exactly one row.

13. Fair-Play Restrictions

The system NEVER calls: Google Maps, geocoding APIs, external business databases, government registries, entity resolution APIs, or any external internet data. All ML processing uses only the supplied challenge dataset.
